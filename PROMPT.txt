带空调项目的时候，选型冷却盘管总要跟装置露点这件事打交道：进来的风一部分贴着盘管冷表面被拉到饱和，剩下那部分没沾着冷面直接绕过去，两路混一起才是出风。这个旁通系数和装置露点没有闭式公式，每次选型都要照着焓湿图手描一遍再迭代凑，一批工况下来很容易描错线导致选型偏保守或偏激进。我想做一个常驻服务，把这套「进口给状态、给旁通或目标出风，服务反算装置露点、旁通系数、出风状态和冷量」的过程钉死，谁都能拿它核对手算结果。

湿空气状态照标准公式展开：给定干球温度、气压，湿度用相对湿度、露点或含湿量三选一表示，都要能换算到统一的含湿量 W；饱和蒸汽压用 Magnus 公式（系数固定写进实现，不要中途换公式）。含湿量超过饱和上限（相对湿度算出来大于 1）时返回结构化错误，不当正常工况处理。

核心是装置露点 ADP：盘管表面存在一点温度 T_adp，处于饱和状态（相对湿度恰好等于 1），出风是「贴着 ADP 饱和的那部分风」与「原样绕过去的旁通那部分风」按旁通系数 BF 混合的结果——出口含湿量 W_out = W_adp + BF×(W_in − W_adp)，出口焓 h_out = h_adp + BF×(h_in − h_adp)，两个量必须用同一个 BF 加权，不允许出口温度单独按算术平均处理导致和含湿量、焓的加权方式不一致。调用方可以给定已知的 BF 直接正算出口，也可以给目标出风温度或目标显热比反过来联立求解 ADP 和 BF，两种模式都要支持，缺失足够条件时返回错误而不是瞎猜。

显热比 SHR 由显热量除以（显热量加潜热量）得到，显热量按干空气比热和进出口温差算，潜热量是总冷量减去显热量，总冷量由进出口焓差乘干空气质量流量得到——这三个量对同一组进出口状态必须自洽，SHR 不落在 (0,1] 区间要拒绝。

边界情况要卡住：装置露点温度必须低于进口湿球温度，且装置露点含湿量不能超过进口含湿量，否则说明这不是一个真正在做冷却去湿的工况（比如目标出风比进口还湿），要返回明确的错误而不是硬凑一个数字出来；旁通系数必须落在 0 到 1 之间；反算装置露点时用的迭代如果不收敛，要返回错误，绝不能把上一次请求算出的中间值当作这次的结果返回。

几条关系要靠自动化测试钉住：旁通系数为 0 时，出口状态必须精确等于装置露点的饱和状态；旁通系数为 1 时，出口必须等于进口且冷量为零；固定装置露点只把旁通系数从 0.1 抬到 0.3，出口含湿量与焓都应该更靠近进口、冷量随之下降；同一进口分别用相对湿度和用露点表示，展开出的含湿量在容差内应当一致，且不能因为输入字段不同就让下游算出的出口结果跳变；显热量加潜热量要等于总冷量（容差内）。

对外提供三个入口：一个接收进口状态加已知旁通系数或目标出风、返回装置露点与出口全部状态量的计算接口；一个只做进口湿空气状态展开供单独核对的接口；一个已知一组进出口状态、只反推显热比和冷量、不做装置露点迭代的接口（用于校验冷却盘管选型报告里报的数字对不对）。内置一个示范工况：夏季常见的三十五度、五成湿常压进风，配一个能手算大致对上的旁通系数，方便任何人拉起服务就核对。

用 Python 3.12 配 FastAPI 实现，饱和蒸汽压、含湿量、焓这几处计算集中在一处，装置露点迭代、旁通加权、显热潜热分解各自独立成模块，不要把整套湿空气状态公式在多个模块里各抄一份、彼此不一致。数据不需要持久化，每次请求独立计算。请按职责拆分成状态展开、装置露点求解、冷量分解、HTTP 路由与校验几个独立文件，基础镜像选 python:3.12-slim，写一份 Dockerfile 让镜像构建好就能跑起来。旁通两端的行为、示范工况的冷量分解、进口字段互推是否一致、几类非法输入能不能被拒绝，这些都要落到随仓的自动化测试里，谁接手都能跑一遍验证。范围限定在这套冷却盘管选型核算，只经 HTTP 提供计算能力，不需要图形界面。
